# jobs-001 Review 1

## Judgment

**blocked**。基础 worker 流程和 SQLite queue claim 已实现，定向测试通过；但尚未满足单 item 成功/失败状态的原子一致性，也没有接入 Bun server 的启动/持续 worker 生命周期。发生进程崩溃或多 worker 实例时，可能留下错误的 durable state，不能作为通过交付。

## Findings

### Blocking

#### P1 — request、文件注册、item/job 终态不是一个事务

- `src/jobs/worker.ts:97-102` 依次调用 `finishRequest`、`registerFile`、`finishItem`，三者是三个独立 repository 操作；失败路径 `src/jobs/worker.ts:104-105` 也分别提交 request 和 item。
- 因此进程可在任意调用之间退出：例如 request 已是 `succeeded` 但 item 仍是 `running`，或文件已写入/注册而 item 仍未完成；job status 也可能继续显示 `running`。这直接违反任务要求“成功失败时 request/item/job 事务一致”，并会影响 stale recovery 和 retry 语义。
- 应提供一个 repository 事务边界（包含 generated file registry 与 request/item/job transition），由 worker 一次提交成功或失败结果；文件写入失败时也要明确只保留可恢复的 durable 状态。

#### P1 — worker 没有接入 server/startup，`recover()` 不是自动启动恢复

- `src/jobs/worker.ts:44-47` 只在显式调用 `recover()` 时执行 stale recovery；`src/jobs/worker.ts:62-65` 的 `start()` 只启动 `drain()`，不会先 recovery。
- 当前 `index.ts:1-3` 仍只调用 CLI `main()`，仓库中没有 Bun HTTP/server worker wiring（搜索 `createWorker` 仅命中 worker 自身和 tests）。所以生产入口不会启动该 server-owned worker，浏览器断开后也没有实际执行者；重启时 queued/stale work 也不会自动恢复。
- 这不是测试 fake 的问题，而是 durable worker 尚未成为应用生命周期的一部分。至少应在 server 初始化后执行 recovery，再启动唯一 worker；若 server wiring 属于后续 api-001，应在本任务交付中明确集成契约并由最终集成测试覆盖，否则 jobs-001 不能判 pass。

### Non-blocking

#### P2 — 已注册输出没有在处理前做幂等短路，stale recovery 测试只验证 DB 去重

- `src/jobs/worker.ts:74-79` 在检查已有文件前就创建新的 request 并调用 provider；已有 `generated_files` 时也会重复生成。
- `src/jobs/worker.test.ts:26-30` 只重复调用 `repo.recoverStale()` 并检查 registry 行数，没有创建真实文件、重启 worker、或验证“已注册输出”不会再次请求 provider。当前同一 item/fileName 的唯一索引能避免重复 registry，但不能避免重复 LLM 成本，也没有校验注册文件是否仍存在/内容完整。

#### P2 — cancellation 只覆盖 queued，不覆盖 claimed-but-not-started 窗口

- `src/db/repositories.ts:51` 只把 `queued` item 改为 `cancelled`；worker 在 `src/jobs/worker.ts:79-83` claim 后立即创建 request 并调用 provider，未在 request 创建前再次检查 job/item 是否已取消。
- 这符合“取消不能中断已开始 provider call”的大方向，但 schema 没有独立 request cancellation 状态，且 claimed 到 provider 调用之间的边界未被测试。建议明确该窗口的语义并增加竞态测试。

#### P2 — 全局并发约束只在单个 worker 实例内成立

- `src/jobs/worker.ts:33-35,49-55` 用实例字段 `active` 保证一个实例 concurrency=1；SQLite claim 本身能避免同一 item 重复 claim，但没有全局 worker lease/单例锁。
- 若 server 误启动两个 worker 实例，两者仍可同时处理不同 items。若“并发1”是应用级要求，需要启动层单例或 DB lease；若仅指每个 worker 实例，应在契约中写清楚。

#### P2 — heartbeat 挂在 item，不是 LLM request

- `src/jobs/worker.ts:80` 和 `src/db/repositories.ts:54` 只更新 `job_items.heartbeat_at`；`llm_requests` schema（`src/db/schema.ts:38-46`）没有 heartbeat 字段。
- 目前 stale recovery 可以据 item heartbeat 工作，但“每个 LLM request 的生命周期/进度”无法独立判断。若 request-level heartbeat 是要求，应补字段或明确 item heartbeat 作为唯一 lease。

#### P3 — provider 错误原文可能被持久化

- `src/jobs/worker.ts:24,104-105` 将 provider/generator 的 `Error.message` 原样截断后写入 request/item error。长度限制能防止无限膨胀，但不能保证错误消息不含 URL、query token、请求头或其他敏感 provider 信息；任务要求明确避免 raw sensitive provider headers。
- 建议使用受控错误分类/脱敏消息，只持久化安全摘要，并将测试覆盖 URL/token/header 样例。

#### P3 — worker 测试覆盖不足，未证明关键崩溃恢复场景

- 现有 `src/jobs/worker.test.ts` 只有 3 个测试：成功后 retry、queued cancellation、DB registry 去重；没有失败事务回滚、写文件后 DB 提交前崩溃、真实 atomic rename/restart、heartbeat stale 期间 recovery、running cancellation boundary、max-attempts 边界或多实例竞争测试。

## Verification evidence

- `bun test`：通过，7 tests / 29 expects（包含 `src/db/repositories.test.ts` 与 `src/jobs/worker.test.ts`）。
- `bun run typecheck`：失败，但错误均来自既有 `src/config.ts:119,125,265-268`；本次审查未发现 `src/jobs/**`、`src/generator.ts`、`src/db/**` 的新增类型错误证据。
- `src/generator.ts:165-186` 已提供单图 API，且没有把凭据放入返回值/业务记录；CLI batch API `generateImages` 仍保留。
- `src/jobs/worker.ts:49-60` 的 queue truth 来自 SQLite `claimNextItem()`，单实例 `active` 使 worker 实例内串行。
- `src/db/repositories.ts:41-44,51-54` 提供 claim、request attempt、终态 job 推导、cancel、retry、stale recovery；这些基础 repository 测试通过。
- 文件名由 job UUID/ordinal 构造（`src/jobs/worker.ts:92`），repository 拒绝 `/`、`\\`、`.` 开头文件名（`src/db/repositories.ts:45`）；未发现凭据写入数据库字段或绝对路径写入 registry 的代码。
- 未修改 `stickers/` 或 `stickers_archived/`。

## Remaining uncertainty

- `api-001` 是否计划负责唯一的 server/worker wiring 尚未在当前代码中出现；如果后续任务承担该 wiring，仍需要在集成阶段证明启动恢复与浏览器无关，并不能消除当前 jobs-001 的交付缺口。
- “并发1”是单 worker 实例级还是整个 Bun 进程/部署级，需要设计文档进一步明确。
- “已注册输出幂等恢复”是否要求验证磁盘文件内容/存在性，当前测试与实现都没有定义该校验。

# db-001 Review 1

## Judgment

**blocked**。当前数据库能用 Drizzle + `bun:sqlite` 完成基本持久化，但还没有完整兑现后续 worker/API 所需的状态机与恢复合同。主要阻塞项是 job 终态不会被 repository 推导、startup recovery 不完整，以及输出登记后没有查询入口。

## Findings

### P1 · blocking — job 永远不会进入成功/失败终态

- 设计位置：`docs/web/README.md:18-20,31-33`；`docs/plan/tasks/db-001.md:36`。Job 是 durable generation request，worker/API 需要从数据库读取可用的 job 状态与进度。
- 代码位置：[src/db/repositories.ts:29](../../src/db/repositories.ts#L29)。`finishItem` 只刷新 `completed_count`/`failed_count`，没有在所有 item 完成后把 job 更新为 `succeeded` 或 `failed`；`claimNextItem` 也只把 job 设成 `running`。
- 影响：所有 item 已成功或失败后，job 仍保持 `running`（重试后也只是 `queued`），后续 worker/API 无法可靠地判断 job 是否完成；这直接违反“job 状态”和成功/失败计数的一致性合同。
- 建议：在同一事务中完成 item transition、计数和 job 状态推导；明确混合结果、全失败、取消中的 running item 等终态规则，并补测试。

### P1 · blocking — startup recovery 只恢复 item，没有恢复 request/job 状态

- 设计位置：`docs/web/README.md:31-33,47-50`；`docs/plan/tasks/db-001.md:36,40`；`docs/plan/analysis/web-ui.md:44`。重启后 SQLite 是 source of truth，worker 应能继续处理崩溃留下的工作。
- 代码位置：[src/db/repositories.ts:33](../../src/db/repositories.ts#L33)。`recoverStale` 只把 stale `job_items` 从 `running` 置为 `queued`，不会把关联 `llm_requests` 的 `running` attempt 置为 `failed`/结束，也不会修复 job 状态或写入相应 request transition。
- 影响：数据库会留下永远 `running` 的 LLM request；恢复后的 item 重新 `startRequest` 虽然会产生新 attempt，但旧 attempt 的状态不再反映崩溃，且 job 可能仍是错误的 `running`/计数状态。无法审计一次 provider 调用是否中断，也可能让后续 API/worker 误判。
- 建议：恢复事务同时处理 stale request、item、job 状态和事件；定义 request 中断状态（或明确将其标记 failed），并测试重启后完整链路。

### P1 · blocking — output registry 没有读取/解析接口

- 设计位置：`docs/web/README.md:34,43`；`docs/plan/analysis/web-ui.md:42,47`。`GET /api/output/:fileName` 必须只通过注册的数据库记录交付文件。
- 代码位置：[src/db/repositories.ts:30](../../src/db/repositories.ts#L30)。只提供 `registerFile`，没有按 id/file name 查询 generated file、按注册记录获得所属 item/job 的 repository 方法。
- 影响：后续 API 无法基于数据库 registry 实现安全的 output delivery，只能绕过 repository 或扫描文件系统，违反“只暴露 registered database records”的边界。
- 建议：提供按 registry id（以及 API 所需的安全 file key）查询的方法，并返回规范化的公开记录；API 仍需在 server-owned 根目录内解析实际路径，数据库不要存绝对路径。

### P2 · blocking — 状态 transition 缺少前置状态校验，repository 可制造非法状态

- 设计位置：`docs/plan/tasks/db-001.md:36-37`；worker 依赖 repository 提供 atomic state transitions。
- 代码位置：[src/db/repositories.ts:27-29](../../src/db/repositories.ts#L27-L29)。`startRequest` 不检查 item 是否为 `running`，可对 queued/succeeded/cancelled item 启动 request；`finishRequest` 不限制当前 request 必须是 `running`；`finishItem` 也不限制 item 当前是 `running`，可重复终结或覆盖既有终态。
- 影响：重试、取消、worker race 或重复回调会破坏 attempt 与 item 状态的一致性；数据库 text 列也没有 CHECK 状态约束来兜底。方法名虽是 transition，但实际不是受保护的状态机。
- 建议：每个 transition 使用期望状态条件并检查 affected row，非法 transition fail fast；为 status 增加 CHECK（或集中 schema/domain 验证），并覆盖重复回调/并发 race 测试。

### P2 · non-blocking — cancel 会无条件把 job 标成 cancelled，且没有处理 job 当前状态

- 设计位置：`docs/web/README.md:49-51`；取消只阻止尚未开始的 provider call。
- 代码位置：[src/db/repositories.ts:31](../../src/db/repositories.ts#L31)。方法只取消 queued items，却无条件更新 job 为 `cancelled`；running item 保持 running，完成后 `finishItem` 只刷新计数，不重新计算 job 状态。
- 影响：取消一个已完成 job、未知 job 或已有 cancelled job 都可能写 event/返回不符合语义的结果；取消含 running item 的 job 会长期留下 running item/job 终态矛盾。若设计允许 running provider 自然完成，需要明确“cancel requested”与最终 job 状态的区别。
- 建议：按 job 当前状态限制 cancel，返回清晰的 no-op/not-found；定义 running item 完成后的最终状态，并在事务内更新。

### P2 · non-blocking — retry-failed 未验证 job 状态，也没有重置/登记 request 生命周期

- 设计位置：`docs/web/README.md:41-42`；`docs/plan/tasks/db-001.md:36,40`。
- 代码位置：[src/db/repositories.ts:32](../../src/db/repositories.ts#L32)。`retryFailed` 无条件把 job 设为 queued，即使不存在 failed item、job 已取消/成功或仍有 running item；它也不清理/标记失败 request（当前主要由 `finishItem` 外部调用保证）。
- 影响：API 重复 retry 或 worker race 时可重新打开不应重跑的 job；状态和 request attempt 历史依赖调用方正确编排，repository 不能独立保证合同。
- 建议：只允许明确的 failed job/failed items，原子返回变更结果；把 retry 的 item/request/event 语义写清并测试“成功 item 不重跑”。

### P2 · non-blocking — asset archive 与 CRUD 语义不完整

- 设计位置：`docs/web/README.md:41`；`docs/plan/tasks/db-001.md:36`。
- 代码位置：[src/db/repositories.ts:18-22](../../src/db/repositories.ts#L18-L22)。有 list/get/create/update/archive，但 `getAsset` 会返回 archived asset，`updateAsset` 可更新 archived asset，且全局唯一 `assets_name_uq` 使归档名称不能被重新创建/复用；没有显式 unarchive 或 not-found/冲突错误包装。
- 影响：API 若按 active asset 语义使用这些方法，可能展示/修改归档数据；归档操作的生命周期未闭合。是否允许归档后复用名称需要设计确认。
- 建议：明确 active/archive 过滤和名称复用策略；对缺失记录、唯一冲突和非法更新提供稳定错误结果。

### P3 · non-blocking — 输入、文件记录和时间约束主要依赖调用方

- 设计位置：`docs/plan/tasks/db-001.md:33-39`。
- 代码位置：[src/db/repositories.ts:10,20,23,30](../../src/db/repositories.ts#L10-L30)，[src/db/schema.ts:3-64](../../src/db/schema.ts#L3-L64)。`count`、`sizeBytes`、name/prompt、mime type、status 等没有 repository/schema 级约束；文件名检查仅拒绝 slash/backslash/`.` 开头，且没有提供 registry 查询。
- 影响：该层若被 API 或 worker 误用，可能写入 count=0/负数、负文件大小或任意 status；安全边界不能只靠未见到的上层校验。
- 建议：在 API 做完整输入验证，同时 repository 对关键不变量 fail fast；文件名允许集合、大小非负、count 范围和状态 CHECK 应有明确合同。

### P3 · non-blocking — 测试覆盖不足，未证明关键合同

- 设计位置：[docs/plan/tasks/db-001.md:40](../tasks/db-001.md#L40) 要求测试 fresh migrate、重开持久化、不可变 snapshot、计数、retry 不重跑成功项、stale recovery。
- 代码位置：[src/db/repositories.test.ts:6-25](../../src/db/repositories.test.ts#L6-L25)。现有仅 2 个测试：基本持久化/一次成功一次失败/一次 retry，以及 item stale recovery；未测试 job 终态、cancel、request transition/recovery、FK/唯一约束、并发 claim、asset archive CRUD、output lookup、错误输入或 retry 成功项不重跑。
- 影响：上述阻塞缺陷均未被回归测试捕获；“retry 不重跑成功项”只间接检查了失败 item 被 claim，没有断言成功 item 不会再次执行。
- 建议：按状态机和事务边界补集成测试，至少覆盖并发 claim、取消 race、重启恢复和约束失败。

- `bun run typecheck`：失败，但错误均位于既有 [src/config.ts](../../src/config.ts)（119、125、265、267、268），本次审查未修改该文件；因此不能据此证明 db-001 全仓 TypeScript check 通过。

## Remaining uncertainty

- `jobs-001`/`api-001` 尚未在本次审查范围内，尚不清楚它们是否会绕过 repository 自行补齐 job 状态、output lookup 或 recovery；即使如此，db-001 任务要求 repository 提供这些 durable transitions，因此不能把缺口视为已满足。
- 取消含 running item 时的最终 job 状态，以及归档 asset 名称是否允许复用，需要设计文档明确；不影响上述 P1/P2 结论。

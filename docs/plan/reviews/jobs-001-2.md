# jobs-001 Review 2

## Judgment

**blocked**。首轮两个 P1 已基本修复：`finalizeRequest` 已把 request、文件注册、item/job 终态放进同一 SQLite transaction；`start()` 先 recovery，`server/index.ts` 也已接入启动与 shutdown 生命周期。定向测试 11 项全部通过。

但仍有两个合同级阻塞问题：错误脱敏会泄漏标准 `Authorization: Bearer <secret>` 头中的 Bearer token；取消在 item 已 claim、但 provider 尚未调用的竞态窗口仍会启动 provider。二者分别违反“不持久化 raw sensitive provider headers”和“取消只允许阻止尚未开始的 provider call”的要求，不能 pass。

## Findings

### Blocking

#### P1 — `Authorization: Bearer` 脱敏不完整，会持久化 secret

- 位置：[src/jobs/worker.ts:10-13](../../../src/jobs/worker.ts#L10)。当前正则把 `Authorization: Bearer` 中的 `Bearer` 当作值替换，但会留下后续 secret。
- 实证：用错误消息 `Authorization: Bearer TOPSECRET x-api-key=KEYSECRET https://provider.test?q=URLSECRET` 运行 worker 后，`llm_requests.error` 与 `job_items.error` 仍包含 `TOPSECRET`。结果类似 `Authorization=[redacted] TOPSECRET ...`。
- 这不是仅测试覆盖不足，而是持久化路径的实际泄漏；provider 错误可包含完整认证头格式。当前 URL 和 `x-api-key=` 样式虽能部分处理，但不能满足合同对 raw sensitive provider headers 的约束。
- 严重度：P1；阻塞性：是。

#### P1 — claim 后、provider 调用前取消仍会调用 provider

- 位置：[src/jobs/worker.ts:45-55](../../../src/jobs/worker.ts#L45)、[src/db/repositories.ts:77](../../../src/db/repositories.ts#L77)。`claimNextItem()` 将 item 设为 `running` 后，worker直接 `startRequest()` 并调用 `generate()`；`cancelJob()` 只把 `queued` item 改为 `cancelled`。
- 如果取消发生在 claim 与 `generate()` 之间，item 仍是 running，worker 不再检查取消标记，因此会启动一个在取消时尚未开始的 provider call。
- 该边界目前没有竞态/阻塞式测试证明。可以通过在 request 创建前再次读取 item/job 状态并原子地确认“not cancelled”，或定义并实现等价的 claim/start 边界来修复；不能靠中断已经开始的 provider 调用解决。
- 严重度：P1；阻塞性：是。

### 已修复项确认

#### request/file/item/job 原子 finalize：通过（数据库层）

- [src/db/repositories.ts:45-60](../../../src/db/repositories.ts#L45) 的 `finalizeRequest()` 使用一个 `db.transaction()`，在同一事务内校验 request/item、终结 request、注册文件、终结 item、刷新派生 job 状态并记录 event。
- 失败时 request/item 的 error 与终态同事务提交；文件 registry 插入失败会回滚该数据库事务，不会留下部分 DB 终态。
- 文件系统写入发生在事务外（[src/jobs/worker.ts:56-58](../../../src/jobs/worker.ts#L56)），因此进程可能在 rename 后、DB commit 前留下 orphan 文件；这不破坏 request/file-registry/item/job 的数据库原子性，但仍是未由测试证明的 crash cleanup 不确定性。

#### start 自动 recovery 与 server lifecycle：通过

- [src/jobs/worker.ts:30-37](../../../src/jobs/worker.ts#L30) 的 `start()` 同步完成 stale recovery 后启动后台 drain loop。
- [server/index.ts:38-59](../../../server/index.ts#L38) 在 server listen 前 `await startGenerationWorker()`，shutdown 时先 `await stopGenerationWorker()`，再停止 server、关闭数据库。符合 web 合同的 server-owned worker 生命周期。

#### 已注册文件幂等复用：基本通过，验证仍偏弱

- [src/jobs/worker.ts:47-49](../../../src/jobs/worker.ts#L47) 先查 registry 并 `stat()` 实际输出；存在时走 [completeRegisteredItem](../../../src/db/repositories.ts#L61)，不会再次调用 provider。
- `finalizeRequest()` 对同 item/fileName 也做 registry 去重（[src/db/repositories.ts:52-56](../../../src/db/repositories.ts#L52)）。
- 现有测试只验证 registry 行数与 queued recovery，尚未真正验证“文件存在 + worker restart/start 后 provider calls 为 0”；因此实现判断为通过但证据不足。另未校验内容/size 与 registry metadata 是否一致，属于合同定义未明确的不确定性。

#### 错误脱敏：不通过

- URL 替换、部分 `key=value` 替换存在，但标准 bearer header 泄漏如上，不能据此判通过。

## Findings

### P1 / blocking — worker 生命周期虽已 wiring，真实 server 集成测试仍缺失

位置：[server/index.ts:38-49](../../../../server/index.ts#L38-L49)、[src/jobs/worker.ts:29-37](../../../../src/jobs/worker.ts#L29-L37)、[server/api.test.ts:30-39](../../../../server/api.test.ts#L30-L39)。

本轮已正确做到：`startServer()` 先 `await createServer()`，再 `await startGenerationWorker(app.worker)`，最后调用 `Bun.serve()`；shutdown 也先 `await stopGenerationWorker()` 再停止 server、关闭数据库。`start()` 同步完成 stale recovery，并将持续 drain loop 作为非阻塞后台任务启动；这与 [设计原文 web/README.md:35](../../web/README.md#L35) 的生命周期合同一致。因此原先“监听前未调用/未等待启动”的 P1 wiring 已修复。

但现有测试并不验证该 wiring：测试调用的是 `createServer()`，随后手动执行 `await app.worker.start()` 和 `await app.worker.drain()`，没有启动 `startServer()`，也没有断言 `Bun.serve()` 发生在 worker 启动之后，更没有验证真实 server 接收的 accepted job 能由后台 worker 执行。测试名称虽称 started worker，实际只覆盖手动组装的 handler/worker 集成。若要求“accepted jobs continuing through the worker”的真实 server 生命周期证据，该 P1 仍是交付阻塞项；至少应增加可控端口的 `startServer()` 集成测试，或把监听注入为可测试依赖。

### 已修复 / 原 P1 — 生产静态路径穿越

位置：[server/index.ts:18-35](../../../../server/index.ts#L18-L35)。

当前先 `decodeURIComponent`，拒绝 NUL，再用 `resolve(dist)` 与 `resolve(distRoot, \`.${requested}\`)` 计算目标，并用 `target === distRoot || target.startsWith(\`${distRoot}/\`)` 做目录边界检查；`/../...`、编码穿越不会越出 dist。SPA fallback 也仅对 `/` 或无扩展名路径返回 `index.html`，不会把带扩展名的资源 typo fallback 成 HTML。原 P1 的直接漏洞已修复。

剩余不确定性：这是 lexical `resolve` 边界检查，不是 `realpath` 边界检查；若 `dist` 内存在指向 dist 外部的恶意 symlink，`Bun.file(target)` 仍可能跟随 symlink。若生产 dist 不允许 symlink，可记录为部署假设；否则应在实际读取前做 realpath 校验。

### 已缓解但仍有契约问题 / P2 — API 路由未全部精确匹配 segment

位置：[server/api.ts:48-53](../../../../server/api.ts#L48-L53)、[server/api.ts:58](../../../../server/api.ts#L58)。

原报告指出的 `GET /api/assets/:id/anything` 已因 `parts.length === 3` 不再命中 GET；但精确匹配没有贯穿所有方法：

- `PATCH /api/assets/:id/anything` 仍进入 `if (req.method === "PATCH")` 并更新资产；
- `DELETE /api/assets/:id/anything` 仍会归档资产；
- job 的 cancel/retry 分支只检查 `parts[3]`，所以 `/api/jobs/:id/cancel/extra`、`/retry-failed/extra` 也可能执行操作。

这些路径不在 [设计原文 tasks/api-001.md:33-37](../../plan/tasks/api-001.md#L33-L37) 定义的公开 API 合同内，却产生状态变更，属于 non-blocking P2；应给每个分支增加精确长度检查并补负向测试。

### P2 / non-blocking — 未知无扩展名静态路径仍返回 200 文本

位置：[server/index.ts:30-35](../../../../server/index.ts#L30-L35)。

本轮已修复“任意未知路径都 fallback 到 index.html”，但不匹配的路径最终仍返回 `200 Sticker Roller server is ready`，而不是 404。若这是明确的 server readiness fallback，应在路由合同中说明；否则资源 typo/未知 URL 仍被掩盖。建议未知静态路径统一 404，或只为明确的健康/根路径保留该响应。

### P2 / non-blocking — malformed output URI 的错误状态不稳定

位置：[server/api.ts:60-62](../../../../server/api.ts#L60-L62)。

`decodeURIComponent(parts[2])` 位于总 try 内，但 URI 解码失败抛出的通常是 `URIError`，不会被 `InputError`/`SyntaxError` 分支处理，因而返回 `500 INTERNAL_ERROR`。畸形 URL 编码应稳定返回 400 或 404，避免把客户端路径错误报告为服务器内部错误。
